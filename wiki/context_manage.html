Context 管理机制

Kilocode 如何在有限上下文窗口内保持长程会话的有效性 · 基于源码的完整技术说明

概述

LLM 的上下文窗口是有限的。随着对话推进，历史消息、工具调用输出、系统提示词会不断累积，最终超出模型限制。Kilocode 采用双层策略管理这一问题：

  • Pruning（轻量修剪） — 每轮对话结束后运行，清除旧工具调用输出，释放少量空间。
  • Compaction（摘要压缩） — 接近上下文上限时触发，将大段历史压缩成结构化摘要，大幅降低占用。
关键认知
Compaction 替换的只是历史（HEAD）部分，系统提示词、工具定义和最近几轮（Tail）始终原文保留。 因此 compact 后的 context 大小 ≠ 摘要大小，而是 系统层固定开销 + 摘要 + Tail。

Context 组成解剖

每次向模型发送请求时，context 由以下部分叠加而成：

┌─────────────────────────────────────────────────────────────┐ │ System Prompt（每轮固定发送，不参与压缩） ~10–16k tokens │ ├─────────────────────────────────────────────────────────────┤ │ Tool Definitions（所有工具 schema，每轮重发） ~2–5k tokens │ ├─────────────────────────────────────────────────────────────┤ │ Editor Context（打开的文件、可见 tab，每轮注入） ~1–3k tokens │ ├─────────────────────────────────────────────────────────────┤ │ Compaction Summary（HEAD 被压缩后的替换物） ~0.5–2k tokens │ ├─────────────────────────────────────────────────────────────┤ │ Tail Turns（最近 N 轮原文保留，可配置） ~10–60k tokens │ ├─────────────────────────────────────────────────────────────┤ │ Current Turn（当前用户输入） ~0.1–5k tokens │ └─────────────────────────────────────────────────────────────┘

新建会话的基础开销（系统提示词 + 工具定义 + 编辑器上下文）通常在 14–24k tokens，这是无论如何都无法消除的固定成本。

Pruning（轻量修剪）

packages/opencode/src/session/compaction.ts  prune()

Pruning 是一个每轮结束后异步执行的轻量过程，只清除旧工具输出的文本内容，不删除消息结构本身。

算法流程

  1. 从最新消息向历史方向扫描，跳过最近 2 轮（不剪最近内容）。
  2. 遇到 compaction summary 消息时立即停止（已压缩区域不再处理）。
  3. 遇到已被标记 compacted 的 tool part 时立即停止。
  4. 累积扫描到的 tool output 估算 token 数。
    超过 PRUNE_PROTECT（40,000 tokens）后，将之后的旧 tool output 加入待剪列表。
  5. 若待剪总量 > PRUNE_MINIMUM（20,000 tokens），才真正执行：
    将每条旧 tool part 的 state.time.compacted 置为当前时间戳，持久化到存储。

关键常量

常量值含义
PRUNE_PROTECT40,000 tokens最近多少 token 的 tool output 受保护，不会被剪
PRUNE_MINIMUM20,000 tokens至少要能剪这么多，才实际执行（避免频繁小操作）
PRUNE_PROTECTED_TOOLS["skill"]这些工具的输出永远不被剪

剪除后的表现

被剪的 tool output 在下次构造 prompt 时会被替换为：

"[Old tool result content cleared]"
当前限制
Pruning 按时间顺序剪旧的（无论内容价值），没有优先级排序。 一个包含关键错误信息的短输出，可能比一堆无意义日志更早被剪。

Compaction（摘要压缩）

packages/opencode/src/session/compaction.ts

Compaction 是重量级操作，将整段历史（HEAD）替换为结构化摘要，大幅节省 token。它由一个专属 compaction agent 完成，可配置为使用不同（通常更便宜）的模型。

溢出检测

packages/opencode/src/session/overflow.ts

每轮 LLM 回复完成后，检查 API 返回的真实 token 计数：

// 使用 API 返回的真实 token 数，不是估算值
const count = tokens.total ||
  tokens.input + tokens.output + tokens.cache.read + tokens.cache.write

const usable = model.limit.input
  ? model.limit.input - reserved          // 有独立 input limit 的模型
  : context_window - max_output_tokens    // 其他模型

return count >= usable                    // true → 触发 compaction
变量默认值说明
reservedmin(20000, max_output_tokens)触发前预留的安全缓冲，可通过 compaction.reserved 覆盖
context = 0 的模型—跳过溢出检测（如自定义模型）
溢出检测精度说明
溢出检测使用 API 回传的真实 token 数，不受 chars/4 估算精度的影响。 中文用户无需担心"该触发时没触发"的问题。

Tail 选择算法

在生成摘要之前，系统需要决定哪些最近的消息保留为"Tail"（原文保留），哪些送入摘要模型（HEAD）。

完整会话历史（旧 → 新） msg[0] user "初始任务" msg[1] asst [tool calls...] msg[2] user "继续" msg[3] asst [more tools...] ... 若干轮 ... msg[N-4] user "倒数第2轮" ←── tail_turns=2 时，从这里开始是 Tail msg[N-3] asst [...] msg[N-2] user "最新一轮" msg[N-1] asst [...] msg[N] user (compaction 触发消息) ────────────────────────────────────────────── HEAD: msg[0] ~ msg[N-5] → 全部送入摘要模型 TAIL: msg[N-4] ~ msg[N] → 原文保留，不压缩

选择逻辑（select()）

  1. 计算 Tail token 预算：
    preserve_recent_tokens 配置项，默认 clamp(usable × 25%, 2000, 8000)。
  2. 取最近 tail_turns（默认 2）个用户轮次。
  3. 从最新轮往前装，每轮估算 token 数（注意：此处用估算值，非真实值）。
  4. 若某轮整体放不下，尝试 splitTurn()：从该轮中间截断，保留能放下的后半段。
  5. 确定 tail_start_id（Tail 起始消息 ID），存入 CompactionPart。
估算精度影响 Tail 边界
Tail 选择用的是 Token.estimate()（基于字符权重），不是 API 真实值。 中文内容修正后（每汉字 ≈ 1 token），精度已大幅提升，但仍是估算。

摘要生成

HEAD 部分（待压缩的历史消息）在送入摘要模型之前经过以下预处理：

  • 媒体剥离：图片等附件替换为 [Attached image/jpeg: filename] 文本占位符。
  • 工具输出截断：每条 tool output 截断到 2,000 字符（TOOL_OUTPUT_MAX_CHARS）。
  • 已压缩部分过滤：上轮 compaction 之前的 hidden 消息不重复处理。

摘要提示词模板

输出格式严格按照以下 8 个区块，LLM 必须保持顺序、保留所有区块：

## Goal
- [单句任务描述]

## Constraints & Preferences
- [用户约束、偏好、规范]

## Progress
### Done        - [已完成工作]
### In Progress - [进行中]
### Blocked     - [阻塞项]

## Key Decisions
- [决策及原因]

## Next Steps
- [有序的下一步行动]

## Critical Context
- [重要技术事实、错误、开放问题]

## Relevant Files
- [文件路径: 为何重要]

增量更新模式

若会话中已存在上一次的 compaction summary，新摘要不从零开始，而是基于旧摘要更新：

"Update the anchored summary below using the conversation history above.
Preserve still-true details, remove stale details, and merge in the new facts."
<previous-summary>...</previous-summary>

历史过滤（filterCompacted）

packages/opencode/src/session/message-v2.ts  filterCompacted()

每次构造 prompt 时，不是把所有消息全部发给 LLM，而是经过过滤：

  1. 从最新消息向历史方向遍历。
  2. 遇到已完成的 compaction user 消息（completed 集合中）：
    • 若 tail_start_id 存在（/compact）：跳到 tail 起点继续收集，忽略 HEAD。
    • 若 tail_start_id 为 undefined（/compact-all）：立即停止，HEAD 完全丢弃。
  3. 最终结果 = Tail 消息 + compaction 消息对（摘要）+ 当前轮。

工具输出实时截断

packages/opencode/src/tool/truncate.ts

工具执行完毕后、结果写入 context 之前，输出大小被检查并按需截断：

参数默认值配置项
最大行数2,000 行tool_output.max_lines
最大字节数50,000 bytes（~50 KB）tool_output.max_bytes
截断方向head（保留开头）每次调用可覆盖

超限时行为：

  1. 将完整输出写入 TRUNCATION_DIR 下的临时文件（7 天后自动清理）。
  2. 返回截断预览 + 提示信息，引导 LLM 用 Grep / Read(offset, limit) 查看完整内容。
  3. 若 agent 有 Task 工具权限，提示改为委托子 agent 处理。

Pruning 对工具输出的处理

Pruning 发生在工具输出已经写入 context 之后，属于事后清理。被 prune 的 tool part 满足：

  • 状态为 completed
  • 工具名不在 PRUNE_PROTECTED_TOOLS（["skill"]）中
  • 未被之前的 compaction 标记过
  • 在距当前 40,000 estimated tokens 之外的旧区域

kilo.jsonc 配置参考

{
  "compaction": {
    // 是否开启自动压缩（溢出时触发）
    "auto": true,

    // 是否开启 pruning
    "prune": true,

    // 保留最近 N 个用户轮次原文（0 = 全部压缩，等同于 /compact-all）
    "tail_turns": 2,

    // Tail 的 token 预算（估算值）
    // 默认: clamp(usable × 25%, 2000, 8000)
    "preserve_recent_tokens": 6000,

    // 触发压缩前预留的安全缓冲（tokens）
    // 默认: min(20000, max_output_tokens)
    "reserved": 16000
  },

  "tool_output": {
    // 单次工具输出最大行数（超出后截断到文件）
    "max_lines": 2000,

    // 单次工具输出最大字节数
    "max_bytes": 51200
  }
}
为长程任务推荐的配置
长程任务（大型重构、多文件修改）中，如果下一步与最近几轮关系不大，可以把 tail_turns 调低到 1 或 0， 或在需要时手动执行 /compact-all 彻底清空 tail。

Slash 命令

命令行为Tail 保留
/compact 手动触发压缩，使用 kilo.jsonc 中的 tail_turns 配置（默认 2） 保留最近 N 轮
/compact-all 压缩全部历史，包括 tail（等效于 tail_turns=0） 不保留

两个命令执行后均不会自动发起下一轮对话（auto=false），等待用户输入。

Token 估算

packages/opencode/src/util/token.ts  Token.estimate()

估算仅用于 Tail 选择 和 Pruning 中的内部预算计算，不影响溢出检测（后者用 API 真实值）。

字符类型估算方式说明
ASCII / Latin 4 chars → 1 token 与主流 tokenizer 吻合
CJK 汉字（U+4E00–U+9FFF 等） 1 char → 1 token 修正前为 0.25 token，低估 4–6×
日文平假名 / 片假名 1 char → 1 token 同 CJK 处理
韩文谚文 1 char → 1 token 同 CJK 处理

覆盖的 Unicode 区段：

U+4E00–U+9FFF   CJK 统一表意文字（常用）
U+3400–U+4DBF   CJK 扩展 A
U+20000–U+2A6DF CJK 扩展 B（生僻字，代理对）
U+F900–U+FAFF   CJK 兼容象形字
U+3040–U+309F   平假名
U+30A0–U+30FF   片假名
U+AC00–U+D7AF   韩文音节
U+1100–U+11FF   韩文字母

限制影响状态
